## What I did

1. **`apps/summaries`** (D-S4): `Consent{id UUID pk, identity FK SET_NULL, kind, version, created_at}`,
   append-only (a `save()` guard refuses updates of an existing row), an index on
   `(identity, kind, version)` for the gate query, and **no PII fields** — no IP, no user-agent, no free text.
   `CURRENT_CONSENT = {"informed": "v1"}` lives in `apps/summaries/constants.py` (code, not env).
2. **`POST /api/consent/`** (`apps/summaries/views.py`): unknown kind/version → `400 {"code":"invalid_consent"}`;
   valid → `201 {kind, version, accepted_at}` + exactly one new row; no method → `405` in the same envelope.
3. **`GET /api/me/`** now returns the consent block: `{"informed": bool, "version": str}`
   (`apps/accounts/permissions.py::consent_state`).
4. **The gate** (`HasInformedConsent`) + **`GET /api/chat/`** placeholder in its final home `apps/chat`
   (T-006 replaces the body, not the gate). Without consent → `403 {"code":"consent_required"}`; with it →
   `200 {"placeholder": true}`.
5. **N-1 — error envelope** (`config/exception_handler.py`, wired as DRF `EXCEPTION_HANDLER`): every DRF error
   body becomes `{"code", "detail"}`; the `code` comes from the exception (a permission/exception can set it),
   otherwise from DRF (`method_not_allowed`, `unsupported_media_type`, …). Existing messages are unchanged;
   non-DRF exceptions are untouched (handler returns `None`). Serializer field errors keep their field map and
   additionally get the envelope keys.
6. **N-2 — no identity for methods the view does not implement.** DRF authenticates before it checks the method,
   so previously a `POST /api/me/` created a row and set a cookie *while returning 405*. Now
   `apps/accounts/contract.py::serves_method()` is consulted by both the authentication class (touch nothing at
   all) and the consent permission (do not answer 403 for a call that is about to be 405).

## Findings / deviations worth the reviewer's eye

1. **N-2 needed a second half.** Making the authentication class skip non-contract methods was not enough: DRF
   checks permissions *before* the method, so an unauthenticated `POST /api/chat/` came back
   `403 not_authenticated` instead of `405`. Fixed by the same helper in the permission
   (`serves_method()`), which yields `405 method_not_allowed` and *no* identity work. Found by the new test
   `test_method_not_allowed_on_every_m1_endpoint` — recorded because it is exactly the kind of “envelope
   normalization” trap the review asked me to close.
2. **`consent.version` semantics** in `/api/me/`: the *accepted* version when consented, otherwise the version the
   server currently requires (so the client can POST it). Documented in `consent_state()` and asserted in tests.
   The contract (`M1-orders-1.md` §1) says `"v1"|null`; `null` can only appear for an identity-less call, which the
   endpoint cannot produce after authentication — kept as a defensive branch, not a live state.
3. **`share` is a known kind but not accepted yet** (`ACCEPTED_KINDS` = current set): `{"kind":"share"}` → 400
   `invalid_consent`. It is the T-022 vocabulary; the model already accepts it.
4. **`/api/chat/` moved to its final app** (`apps/chat`) instead of living in `accounts`: T-006 fills the same
   file rather than moving it later.
5. **Unowned 404s stay Django's** (not wrapped in the envelope) — recorded in a test so the boundary is explicit.
